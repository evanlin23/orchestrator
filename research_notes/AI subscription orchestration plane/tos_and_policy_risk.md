# Terms-of-service and account-enforcement risk of orchestrating consumer AI subscriptions (as of 3 Nov 2026)

Labels used on each finding: **[Policy]** = official vendor legal or documentation text; **[Staff]** = statement by a named vendor employee; **[Press]** = tech press coverage; **[Community]** = user reports (GitHub issues, forums, HN, Reddit, X). "Fetched 2026-11-03" means the page was read on that date and showed that text then.

## Anthropic (Claude Pro/Max): automated access, OAuth in third-party harnesses, Agent SDK / `claude -p`, multiple Max accounts, account sharing, headless CI, weekly limits

### Takeaway
Anthropic's rule, enforced since January 2026 and formalised in 2026 docs, is clear. A Claude subscription may drive the **unmodified official Claude Code binary**, plus the Agent SDK and `claude -p`, for "ordinary, individual" use, including headless runs and the official GitHub Action via `CLAUDE_CODE_OAUTH_TOKEN`. Using subscription OAuth tokens in any third-party harness, spoofing the Claude Code client, or intermediating or reselling credentials is not allowed. Since 4 Apr 2026, third-party harness usage is billed separately as "extra usage" and no longer comes out of plan limits. An Anthropic staffer said in Feb 2026 that two Max accounts are not against the terms. Some users still report automated bans, and the published terms never address multiple accounts.

### Cited Findings
**Consumer Terms (official text; page shows "Effective Oct 8, 2025", fetched 2026-11-03)**
- [Policy] §3.7 prohibits: "to access the Services through automated or non-human means, whether through a bot, script, or otherwise". The exception: "Except when you are accessing our Services via an Anthropic API Key". — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- [Policy] §3.4 prohibits: "To crawl, scrape, or otherwise harvest data or information from our Services other than as permitted under these Terms". §3 also bars bypassing "any of our systems or protective measures". — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- [Policy] §2 on sharing: "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else", "You also may not make your Account available to anyone else", and "You are responsible for all activity occurring under your Account". — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- [Policy] §3.2 bars reselling the Services ("or resell the Services") and using them "To develop any products or services that compete with our Services". — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- [Policy] The Consumer Terms have **no provision on holding multiple accounts**. Neither permission nor prohibition was found. — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)

**Claude Code "Legal and compliance" doc (no date shown; fetched 2026-11-03). This is the operative rule for subscriptions.**
- [Policy] Claude Code on Free/Pro/Max/Ultra plans is governed by the Consumer Terms. Team/Enterprise/API use is governed by the Commercial Terms. — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- [Policy] "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK." — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)

- [Policy] "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication… Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. ### Inferences
- The clearest line is **binary provenance plus who the user is**. The unmodified `claude` binary, the Agent SDK and `claude -p`, run by the subscriber for their own work, are explicitly contemplated, including headless and CI use via `claude setup-token`. Re-using the OAuth token in any other client, or forging Claude Code headers, is the enforced violation. An orchestrator that **spawns `claude -p` / Agent SDK processes** for the user's own tasks stays inside Anthropic's documented lines. An orchestrator that extracts the token and calls the Messages API itself, or puts a proxy in front of it, does not.
- "Ordinary, individual usage" is the operative qualifier for limits. The weekly limits were introduced specifically because of 24/7 background use and account sharing. Continuous unattended loops that keep two Max accounts saturated around the clock are exactly the usage pattern Anthropic named. That makes rate-limiting and abuse review more likely, even if it is not an explicit ToS breach.
- Holding two Max 20x subscriptions appears tolerated, per a staff statement rather than terms text. Each account must belong to the same individual and must not be used by anyone else (§2). Rotating between accounts specifically to evade limits is not addressed in text. It could be read under §3's "bypass… protective measures"; that is a reading, not a finding.
- §3.7 literally bars "automated or non-human means… script" except via API key. Anthropic's own docs sanction `claude -p` and Agent SDK scripting on subscriptions, so in practice the docs narrow §3.7. The terms text itself was not amended as of the Oct 8, 2025 version.

### Gaps
- I could not access Thariq's original X posts. Quotes come via PiunikaWeb and VentureBeat, and individual post dates within Feb 2026 are not given.
- No Anthropic text explicitly addresses running Claude Code on a **VPS 24/7** with a subscription token. The GitHub Action docs support CI. "Ordinary, individual usage" is undefined.
- The 15 Jun 2026 support notice says "third-party app usage still draw[s] from your subscription limits". That appears to conflict with the 4 Apr 2026 "extra usage" billing for third-party harnesses. I could not resolve which "third-party apps" that sentence means.
- One aggregator claimed that third-party harness access was reinstated in mid-May 2026 behind a "programmatic credit". I found no second source, so it is unverified.
- Anthropic's Usage Policy (AUP) text on automation was not separately fetched. The ToS and Claude Code docs carry the relevant provisions.

## OpenAI (ChatGPT Plus / Codex): automated extraction, programmatic access, Codex ChatGPT sign-in in third-party tools, enforcement

### Takeaway
OpenAI is the most permissive vendor. Its Terms of Use ban programmatic extraction and account sharing. But the Codex lead publicly invited users to use ChatGPT sign-in in third-party harnesses (OpenCode, Pi), and OpenAI worked with OpenCode on it from Jan 2026. Codex docs document ChatGPT-token use on "trusted scripts, schedulers, and private CI runners", while recommending API keys for automation. OpenAI staff said in Aug 2026 that "sub2api" (turning a subscription into a shared API) is not supported. I found no documented wave of OpenAI bans for harness use.

### Cited Findings
- [Policy] OpenAI Terms of Use (version effective 11 Dec 2024, via archive mirror), under "What you cannot do": "Automatically or programmatically extract data or Output", "circumvent any rate limits or restrictions or bypass any protective measures or safety mitigations", and "Use Output to develop models that compete with OpenAI". — [OpenAI ToU 2024-12-11 (mirror)](https://open.windriver.com/info/uni-license-list/licenses/openai-tou-20241211.html)
- [Policy] Same ToU, on registration: "You may not share your account credentials or make your account available to anyone else". On termination: "We reserve the right to suspend or terminate your access to our Services or delete your account". — [OpenAI ToU 2024-12-11 (mirror)](https://open.windriver.com/info/uni-license-list/licenses/openai-tou-20241211.html)
- [Policy-secondary] The current en-GB and Rest-of-World versions carry the same automated-extraction language. A RoW page marks a "previous version effective January 1, 2026", so newer revisions exist. — [OpenAI ToU en-GB](https://openai.com/en-GB/policies/terms-of-use/); [OpenAI RoW revision](https://openai.com/policies/row-terms-of-use/revisions/2024-12-11/)
- [Policy] Codex auth docs (fetched 2026-11-03): "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs." "API keys are still the recommended default for automation." "Access tokens are intended for trusted scripts, schedulers, and private CI runners." "Don't expose Codex execution in untrusted or public environments." "Treat `~/.codex/auth.json` like a password… Don't commit it, paste it into tickets, or share it in chat." Headless guidance is to prefer device-code auth or "copy your cached credentials to the headless machine". — [Codex Authentication docs](https://learn.chatgpt.com/docs/auth) (redirected from developers.openai.com/codex/auth)
- [Staff] 9 Jan 2026 (date from post ID), Tibo Sottiaux (Codex lead) on X: "We are working with OpenCode to allow Codex users to use their Codex subscriptions and usage limits in OpenCode directly. Also exploring how to support other awesome actors in the space." — [X @thsottiaux](https://x.com/thsottiaux/status/2009742187484065881)
- [Staff] 23 May 2026 (date from post ID), Sottiaux: "About 5% of our production traffic is on the Pi harness, about another 5% is on OpenCode. Reminder you can use your ChatGPT account in a flourishing set of other tools." — [X @thsottiaux](https://x.com/thsottiaux/status/2058071172361998482)
- [Press] OpenAI's Codex for Open Source program says "Developers should code in the tools they prefer" and lists OpenCode, Cline, pi and OpenClaw as supported tools. The article also says OpenAI's terms neither explicitly permit nor prohibit using a subscription in non-OpenAI tools. — [Manifest blog, 2026-07-01](https://manifest.build/blog/chatgpt-plus-tokens-third-party-harnesses/)
- [Press] OpenAI launched "Sign in with ChatGPT" so Plus/Pro users can spend plan allowance inside participating third-party developer tools. Reported partners include Devin, Warp, Notion, OpenCode and Pi, reportedly at DevDay 2026. — [The New Stack](https://thenewstack.io/sign-in-with-chatgpt/); [explainx.ai](https://explainx.ai/blog/openai-sign-in-with-chatgpt-devday-2026)
- [Community] OpenCode has a built-in ChatGPT Plus/Pro login (changelog v1.1.11). — [learnopencode changelog](https://learnopencode.com/en/changelog/v1.1.11.html)
- [Staff-secondary] ~23 Aug 2026: Sottiaux replied "We don't support sub2api", meaning gateways that pool or convert subscriptions into an API. A PSA relaying this says "There's no confirmed ban policy yet, but it may put your account at risk." — [X @hqmank PSA](https://x.com/hqmank/status/2091541490959081977?lang=en); [Inspire2rise](https://www.inspire2rise.com/openai-cracks-down-codex-api-reselling-loophole.html)
- [Community] One forum post reports a Codex + ChatGPT Pro account banned without explanation. The user says they used no proxy and suspects a datacenter IP. This is a single anecdote. — [OpenAI Developer Community](https://community.openai.com/t/codex-chatgpt-pro-account-banned-with-no-warning-no-explanation-18-month-subscriber/1381906)
- [Community] A Codex GitHub issue notes there is no documented public API for the ChatGPT-subscription credential, which is not valid against api.openai.com. — [openai/codex #36886](https://github.com/openai/codex/issues/36886)

### Inferences
- For the ChatGPT Plus subscription, three paths look sanctioned: the official Codex CLI (`codex exec`), a Codex GitHub/CI flow on a private runner, and harnesses that OpenAI staff named (OpenCode, Pi) or the "Sign in with ChatGPT" program covers. OpenAI's openness is policy by staff statement and partnership. The ToU text still bans programmatic extraction, so OpenAI could tighten it.
- Turning the Plus login into a general OpenAI-compatible endpoint (sub2api/CLIProxyAPI style), especially one serving other users, is the pattern OpenAI staff explicitly disowned.
- Running Codex from a VPS or datacenter IP may draw risk-system attention, based on one anecdote. Codex docs also say not to expose execution in untrusted or public environments.

### Gaps
- I could not fetch the current OpenAI Terms of Use (HTTP 403). Verbatim text is from the 11 Dec 2024 version, and a 1 Jan 2026 or later revision exists.
- I found no OpenAI primary page confirming the "Sign in with ChatGPT" partner list or launch date, only secondary coverage.
- I found no OpenAI statement on multiple ChatGPT accounts per person, which is the user's case only if they add more.
- I found no confirmed OpenAI ban wave tied to third-party harnesses or CLIProxyAPI.

## Google (Google AI Plus / AI Pro, Gemini CLI to Antigravity CLI, Antigravity): third-party use of OAuth, the 2026 suspensions, multiple accounts

### Takeaway
Google's text is the strictest. Both the Gemini CLI docs and the Antigravity Additional Terms say that using third-party software to access the service with the CLI/Antigravity OAuth login (e.g., OpenClaw) is a breach that can lead to suspension. Google enforced this in large waves in Feb 2026 and again around Sep 2026, including against paying AI Pro and Ultra subscribers. Suspensions mostly hit the Antigravity/Gemini CLI service rather than the whole Google account. Google's own CLI officially supports headless `agy -p` for scripting and CI. Whether *another program* launching the official `agy` binary is covered by the ban has been asked repeatedly and has no official answer.

Also: "If you would like to use a third-party coding agent with Gemini, the supported and secure method is to use a Vertex AI or Google AI Studio API key." — [Gemini CLI FAQ (repo)](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/resources/faq.md)

### Inferences
- For the two Google AI Pro accounts and the AI Plus account, the safe path is Google's own surfaces: the Antigravity app, the `agy` CLI, including headless `-p` as documented for scripts and CI, the Gemini app, and official IDE extensions. Third-party clients using the Google OAuth token (OpenClaw, OpenCode plugins, CLIProxyAPI, Antigravity proxies) are the explicitly named and repeatedly enforced violation.
- An orchestrator launching the official `agy -p` binary as a subprocess is the grey zone. It matches the documented headless/scripting use case. But the clause "using the Service in connection with products not provided by us" is broad, Google has not clarified it, and Google's detection has produced false positives.
- Pooling several family-plan or multiple Google accounts behind one proxy correlated with mass suspension (5 of 6 accounts). Two individually owned AI Pro accounts used through official clients is a different pattern. No policy text addressing it was found.
- Reported suspension scope is usually the Antigravity/Gemini CLI service. A few unconfirmed reports claim the whole Google account. For a primary Google account (Gmail, Photos), even the low-probability whole-account outcome is the largest downside of any vendor here.

### Gaps
- I found no Google policy text on one person holding **multiple Google accounts each with a Google AI subscription**. Google One family sharing exists, but its terms were not fetched.
- The Google AI Plus tier terms were not separately located. The Gemini CLI page lists only Pro/Ultra.
- One search summary mentioned a Google "abuse-mitigation policy effective 2026-03-25" naming Gemini CLI OAuth with third-party software. I could not locate or verify it.
- I found no official Google statement confirming that scripted invocation of `agy` by another local program is permitted, and none on running `agy` on a VPS or in GitHub Actions with a consumer subscription.
- The Feb 2026 "full reversal" of bans is single-sourced (MetricNexus) and unverified.

## Meta (Meta AI app / Muse Spark free tier): automated access

### Takeaway
The Meta AI-specific terms don't address automation. Meta's general platform terms, which cover Meta AI as a Meta Product, prohibit automated access or data collection without prior permission, password and account sharing, and creating more than one account. Meta offers no consumer CLI or OAuth agent path for Muse. Its developer path is a separate paid Muse Spark API. I found no enforcement incidents.

## Subscription-to-API proxies (CLIProxyAPI, claude-code-proxy/ccproxy, Antigravity proxies, sub2api, Copilot API proxies): risk profile and known bans

### Takeaway
These proxies are the highest-risk pattern. Each extracts a consumer OAuth token and re-presents it as an OpenAI- or Anthropic-compatible endpoint. Every vendor's text or staff names this pattern: Google ("harvest or piggyback"), Anthropic ("collect, store, or intermediate… credentials"; spoofing), and OpenAI ("We don't support sub2api"). Most documented bans come from Google users of CLIProxyAPI and Antigravity proxies, with scattered Claude cases. GitHub Copilot proxies carry abuse-detection warnings in their own READMEs.

### Cited Findings
- [Policy] Google: third-party tools that "harvest or piggyback on Gemini CLI's OAuth authentication" violate terms and risk "immediate suspension or termination". — [Gemini CLI FAQ](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/resources/faq.md)
- [Policy] Anthropic: developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" or "route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users". — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- [Staff-secondary] OpenAI (Sottiaux, ~Aug 23, 2026): "We don't support sub2api." — [X PSA](https://x.com/hqmank/status/2091541490959081977?lang=en)
- [Community] CLIProxyAPI users report permanent Google suspensions, with the stated reason "logging in using third-party software", and pooled family-plan accounts mass-blocked from Antigravity. — [CLIProxyAPI #1803](https://github.com/router-for-me/CLIProxyAPI/issues/1803); [#1814](https://github.com/router-for-me/CLIProxyAPI/issues/1814); [discussion #1558](https://github.com/router-for-me/CLIProxyAPI/discussions/1558)
- [Community] Claude subscription disabled "after an automatic review of your recent activities", reported in the CLIProxyAPI tracker. The client was OpenCode, and the proxy link is not established. — [CLIProxyAPI #2211](https://github.com/router-for-me/CLIProxyAPI/issues/2211)
- [Community] Some sub2api forks are literally CLIProxyAPI repackaged as a Cloudflare Worker. Some resellers market "zero risk of account suspension", which contradicts OpenAI's stance. — [PlaygrndLabs/sub2api](https://github.com/PlaygrndLabs/sub2api); [Inspire2rise](https://www.inspire2rise.com/openai-cracks-down-codex-api-reselling-loophole.html)
- [Community] Copilot API proxy READMEs relay a GitHub security notice that excessive automated or scripted Copilot use "may trigger GitHub's abuse-detection systems", and warn of possible "temporary suspension of your Copilot access". They describe the tools as reverse-engineered and unsupported. — [betaHi/copilot-api](https://github.com/betaHi/copilot-api); [coproxy docs](https://docs.rs/crate/coproxy/latest)
- [Community] Some proxy projects maintain "ban detection" documentation, which shows bans are an expected operational hazard. — [OmniRoute wiki: Ban Detection](https://github.com/cheaper-inference/OmniRoute/wiki/Ban-Detection)
- [Community] The OpenClaw maintainer attributed detection to "auth header mismatches and users calling unsupported models", meaning the proxied traffic is fingerprintable. — [openclaw/openclaw #14203](https://github.com/openclaw/openclaw/issues/14203)

### Inferences
- Proxies fail on several counts at once. They use the token outside the official client, they often spoof client headers, and they enable pooling or sharing. Each count is independently named in vendor text or by vendor staff. They also produce distinctive traffic fingerprints. For the Anthropic and Google subscriptions, this pattern has the most documented bans. For OpenAI it is officially unsupported, though I found no confirmed ban wave.
- Proxies that wrap the official SDK/CLI, such as `opencode-claude-max-proxy` on Anthropic's Agent SDK, sit in between. The token never leaves the official binary. But the purpose, serving a third-party harness, is what Anthropic's 4 Apr 2026 change addressed, and the project's own README says Anthropic doesn't allow it.

### Gaps
- I found no vendor statements about specific proxies by name (CLIProxyAPI, ccproxy, claude-code-proxy). Ban attribution to a specific proxy rests on self-reports.
- I found no official GitHub statement on Copilot proxies, only README-relayed notices.

## General principle: what is clearly fine, grey, and clearly against terms

### Takeaway
Across vendors, the sanctioned pattern is **the vendor's own unmodified client, signed in by the subscriber, doing the subscriber's own work**. That includes the vendor's official headless or print mode and official CI/GitHub integrations. Grey: a personal orchestrator that launches those official CLIs as subprocesses and hands work between them, and heavy 24/7 unattended loads. Clearly prohibited: extracting OAuth tokens into other clients or proxies, spoofing client headers, sharing or pooling accounts, reselling, and scripting consumer web UIs. OpenAI is the exception, since it explicitly welcomes some third-party harnesses.

### Cited Findings
- [Policy] Clearly fine (Anthropic): an end user "signing in to the unmodified Claude Code binary with their own Claude subscription"; the Agent SDK and `claude -p` drawing on subscription limits; `CLAUDE_CODE_OAUTH_TOKEN` in the official GitHub Action. — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance); [Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan); [claude-code-action setup](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md)
- [Policy] Clearly fine (Google): Antigravity CLI headless `-p` "to script agent tasks, integrate with CI pipelines". — [Antigravity headless docs](https://antigravity.google/docs/cli/headless/)
- [Policy/Staff] Fine with caveats (OpenAI): Codex ChatGPT tokens on "trusted scripts, schedulers, and private CI runners", with API keys "recommended default for automation". Third-party harnesses such as OpenCode and Pi are invited by the Codex lead. — [Codex auth docs](https://learn.chatgpt.com/docs/auth); [X @thsottiaux, 2026-05-23](https://x.com/thsottiaux/status/2058071172361998482)
- [Policy] Clearly prohibited: third-party OAuth use (Google, Anthropic), client spoofing (Anthropic, Jan 2026), credential sharing ("may not share your Account login information" for Anthropic; "may not share your account credentials" for OpenAI; "Not share your password" for Meta), reselling (Anthropic §3.2), and scraping or automated extraction from web UIs (Anthropic §3.4/3.7, OpenAI "programmatically extract", Meta "automated means"). — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms); [OpenAI ToU (2024-12-11 mirror)](https://open.windriver.com/info/uni-license-list/licenses/openai-tou-20241211.html); [Meta Terms](https://www.facebook.com/terms.php); [Antigravity Terms](https://antigravity.google/terms?hl=en); [VentureBeat, 2026-01-09](https://venturebeat.com/technology/anthropic-cracks-down-on-unauthorized-claude-usage-by-third-party-harnesses)
- [Press] Usage-pattern risk: Anthropic's weekly limits explicitly targeted "continuously in the background, 24/7" use. Google cited backend strain ("tremendously degraded the quality of service"). Anthropic cited "usage patterns of these third-party tools". — [TechCrunch, 2025-07-28](https://techcrunch.com/2025/07/28/anthropic-unveils-new-rate-limits-to-curb-claude-code-power-users/); [Wikipedia: Google Antigravity](https://en.wikipedia.org/wiki/Google_Antigravity); [TechCrunch, 2026-04-04](https://techcrunch.com/2026/04/04/anthropic-says-claude-code-subscribers-will-need-to-pay-extra-for-openclaw-support/)

### Inferences
- **Lowest-risk architecture:** a local coordinator that invokes `claude -p` or the Agent SDK (Claude Max accounts), `codex exec` (ChatGPT Plus) and `agy -p` (Google AI Pro) as subprocesses, each signed in through the vendor's own login flow. It passes work as files, prompts or git branches, never as tokens. This keeps every request inside an official client. Handing work between agents is then just one official CLI's output becoming another's input on the user's machine. No vendor text reviewed prohibits that, but none explicitly blesses cross-vendor orchestration either. For Google specifically, the "in connection with products not provided by us" clause leaves this unresolved.
- Per-vendor risk ranking for subprocess orchestration of official CLIs, from the evidence above: OpenAI lowest (explicit openness), Anthropic low (explicitly documented for `claude -p`/SDK, with an "ordinary, individual" caveat), Google moderate (strict clause, aggressive and sometimes erroneous enforcement, no staff clarification on wrapper scripts), Meta not applicable (no official CLI, and UI automation is prohibited).
- For GitHub Actions or VPS hosting: Anthropic documents the subscription token in its Action, Google documents a CI example for `agy`, and OpenAI documents private trusted runners but recommends API keys. Running all of these 24/7 on rotating accounts edges toward the usage patterns vendors cited when tightening limits.
- Two Claude Max accounts: keep them strictly as the same person's accounts, each in its own official client. Don't move one account's token to another machine shared with others, and don't use the second account mainly to defeat the first's limits. Anthropic staff said multiple Max accounts are fine. The terms are silent, and they forbid bypassing "protective measures".

### Gaps
- No vendor has published an explicit statement on **cross-vendor agent orchestration** where one vendor's official agent invokes another vendor's official CLI.
- Enforcement is largely automated and opaque. False positives are documented for Anthropic (Jan 2026) and Google (Sep 2026 HN reports), so compliance with the written terms does not guarantee no suspension.
- This note reports what the documents and incidents say. It is not legal advice.
